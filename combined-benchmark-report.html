Within-study findings

  • Across the original five machines, the Ryzen desktop was fastest at every worker count. The ThinkPad finished one workflow faster than either Mac, while both Macs were faster at three and four workers.
  • In the paired image experiment, XFS was faster than the Btrfs image in all ten pairs at both three and four workers. The Btrfs image won all ten one-worker pairs. The two-worker difference was small.
  • At four workers: XFS image 12.945 s, Btrfs image 22.236 s, and fresh native Btrfs control 16.334 s. The image-backed Btrfs penalty is a material reason not to treat this as a bare-metal XFS speedup.

Shared workload and study differences

Reproduction and timing protocol
  • Repository eventpop/eventpop, commit 0e0499f42444f1e4b2c0a6d11fc8043b42be295a, 10,055 tracked files. pnpm 11.18.0, PATH Node 24.22.1. pnpm has its own packaged runtime; embedded Node v26.0.0 was verified for the identical Linux wrapper.
  • All eight datasets have ten measured batches at each of 1, 2, 3 and 4 workers. The source commit, lockfile hash, tool versions and workload settings were validated before combining. Raw samples are preserved without pooling datasets.
  • Per batch: parallel detached Git checkout, barrier, parallel offline frozen dependency installation with build scripts disabled, barrier, parallel tree deletion. The original batch implementation is reused in the follow-up.
  • Per-machine monotonic clocks measure phase wall times. Total is the sum of phase wall times. Git metadata pruning, downloads, provisioning and SSH latency are outside the timers. Ruby dependencies, Rails/database setup and native install scripts are excluded.
  • Original study: one warmup batch per worker count, then ten measured rounds with worker order seed 42, independently on each machine.
  • Onarchy follow-up: one warmup plus one excluded preflight per worker count, then ten paired rounds. Worker order seed 42; filesystem-case order seed 73 at each worker count. Cases run sequentially.
  • Both 16 GiB image files were verified fully preallocated, with outer NOCOW/NODATASUM on Btrfs. Guest Btrfs uses noatime, zstd:3, ssd and nodiscard. Guest XFS uses noatime/nodiscard with metadata CRC and reflinks enabled. Both remain layered over Btrfs/LUKS/NVMe; no existing partition was reformatted.
  • Automatic package imports used clones on Btrfs/APFS/XFS and hard links on ext4. Platform-specific optional dependencies differ: 1,318 installed packages on Linux and 1,319 on macOS.
  • Plain XFS was measured. VDO, the separate block-level compression/deduplication layer discussed in the video, was not tested. Linux VDO documentation.
Reliability, excluded data and interpretation limits
  • 320 successful measured batches and 1 failed measured attempt across the eight datasets. The M4 Pro's parallel Git commondir read failure was saved after 33 successful batches; seven missing samples were resumed using the original batch function. Failed-attempt latency is excluded from successful timings, and the error remains in the evidence.
  • The first XFS pilot had unequal backing allocation because mkfs.xfs recreated a sparse file. It was stopped, cleaned up and excluded in full. Corrected allocation checks and pilot records are retained separately. Pilot and preflight timings are not part of the 320-batch summary.
  • This is a warm, uncontrolled-cache workload with no fsync, durability test or cache eviction. No flush separates paired cases, so asynchronous writeback from earlier cases can overlap later cases.
  • CPUs, RAM, SSD/HDD hardware, compression, encryption, mount options, free space, power states, OS/Git/Python versions and background activity differ. The cross-machine results cannot isolate APFS, Btrfs or ext4. The layered follow-up cannot establish bare-metal XFS performance.
  • Debian's HDD run showed high I/O wait, active swapping and wide variation. A Mac snapshot showed fseventsd CPU activity. These are observed contexts, not causal proof. Ten samples per worker count support descriptive medians and ranges; small differences are not proof of statistical significance.

Cleanup and evidence

Temporary stores, dataset copies, mounts and images from both studies are removed. Original Eventpop checkouts were preserved. Raw timings, inventories, logs, cleanup receipts and source remain available; xfsprogs/liburcu were installed for the XFS follow-up.
